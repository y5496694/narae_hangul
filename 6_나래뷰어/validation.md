## 재현한 오류와 수정

- 수정한 문단과 오래된 줄 좌표가 섞인 HWPX가 3쪽으로 나뉘던 문제: 수정 후 이어지는 본문을 새 흐름에서 배치해 한컴과 같은 2쪽으로 수정했습니다. 캐시 없는 빈 문단의 줄 간격도 포함합니다.
- 음수 자간이 적용된 HWP 문단 끝 제어 문자가 가운데 정렬을 밀던 문제: 보이는 글자와 인라인 개체의 UTF16 위치를 유지하면서 끝의 제어 패딩을 제거했습니다.
- 같은 사각형이 HWP/HWPX에서 서로 다른 그리기 경로로 가던 문제: 실제 도형 좌표에 따라 사각형 테두리 경로를 선택하고 직렬화 정밀도 차이를 정규화했습니다.
- Windows의 offscreen Qt가 설치 글꼴을 못 읽던 문제: 창을 표시하지 않는 일반 Windows Qt 플랫폼을 사용합니다.
- PDF 투명 배경 때문에 검정 글자 차이가 사라지던 문제: 흰 종이에 합성한 RGB로 비교합니다. 둘째 쪽만 바꾼 문서·누락된 쪽·내용이 다른 문서를 실패로 잡는 회귀 검사를 포함합니다.
- 문서에 저장된 2쪽 모아 찍기 때문에 9쪽이 PDF 5쪽으로 출력되던 문제: 설치된 `PrintToPDFEx`의 PDF 장치를 유지하고 전체 1쪽 인쇄를 명시해 9쪽으로 출력합니다. `SaveAs(PDF)`의 저장된 인쇄 설정을 그대로 이어받지 않습니다.
- 한컴 제어 객체의 활성 문서가 None인 경우 닫기를 건너뛰고 파일을 잠가 두던 문제: 소유한 문서 ID로 재활성화합니다. 두 제어 객체의 닫기 순서를 바꿔도 파일 잠금이 해제되는 실제 검사를 했습니다. CLI 프로세스 간 활성 문서 충돌은 Windows mutex로 직렬화합니다.
- 잘라낸 그림을 뒤집으면 선택한 원본 영역까지 바뀌던 문제: 전체 비트맵을 먼저 뒤집는 대신 잘라낸 표시 사각형에 반전을 적용했습니다. 한컴에서 직접 좌우·상하 뒤집기 후 저장한 HWP/HWPX 각각 4개 조합으로 선택된 그림 내용이 유지됨을 확인했습니다. 이 검사는 그림 내용 검사이며 JPEG 압축·가장자리 좌표의 픽셀 일치를 의미하지 않습니다.
- 그림 효과의 누락된 진단: 미지원 색상 효과와 한컴 PDF 투명도 점무늬의 차이를 `warnings`와 `layout.image_limitations`에 기록합니다. 전용 스킬도 이 필드를 확인하도록 갱신했습니다.

## 회색조·흑백과 HWP 그림 속성

회색조와 흑백 표시를 구현했습니다. 원본 비트맵의 알파를 유지하며, 변환한 그림은 PDF에서 무손실로 저장해 추가 JPEG 색상 오차를 피합니다. HWP/HWPX 각각 두 효과·256개 색상 영역, 총 1,024개 내부 표본 픽셀이 한컴 PDF와 정확히 같았습니다. 원본 비트맵 알파 보존과 흑백 128/129 경계도 검사했습니다. 이는 검사한 색상 표본의 일치이며 쪽 전체의 가장자리·좌표·해상도 일치는 아닙니다.

한컴 2024가 HWPX에서 HWP로 저장한 밝기·대비를 각각 달리한 5개 경우에서 HWP 그림 레코드의 68바이트는 대비, 69바이트는 밝기였습니다. [공식 HWP 5.0 문서](https://cdn.hancom.com/link/docs/한글문서파일형식_5.0_revision1.3.pdf)의 표 32에 적힌 순서와 달랐습니다. 읽기와 쓰기를 함께 고쳤으며, 나래가 생성한 HWP와 HWPX를 한컴으로 출력한 5쪽 전체가 픽셀까지 일치했습니다. 자체 저장·읽기만으로 순서를 검증하지 않았습니다. 밝기·대비의 독립 표시도 아래와 같이 구현했습니다.

지원하지 않는 `PATTERN8x8` 효과를 흑백으로 잘못 읽던 분기도 고쳤습니다. 이 값은 보존하고 `image_limitations`에 표시합니다. 한컴 PDF 투명도의 남은 차이와 미지원 색상 효과는 계속 진단합니다.

## 밝기·대비·투명도와 글꼴 추가 검증

밝기·대비의 정수 계산과 특이 경계값, 원본 알파에서 그림 alpha 바이트를 빼는 규칙을 구현했습니다. 회색조 → 밝기·대비 → 흑백 순서도 반영했습니다. HWP/HWPX 각각 29개 조합·256개 색상 영역, 총 **14,848개 내부 표본 픽셀**이 한컴 `PrintToImage`의 96 dpi PNG와 정확히 같았습니다. PDF 프린터는 투명도를 8×8 점무늬 마스크로 출력하는 별도 경로를 사용하므로 이 일치를 한컴 PDF 전체의 일치로 확대하지 않습니다. 이전 단계의 미지원 점무늬는 아래 추가 작업에서 구현했습니다. 남은 시작 위치·좌표·원본 알파 차이는 세부 진단으로 구분합니다.

한양 신명조·중고딕의 한자·일본어·특수문자 HFT를 추가하고 설치된 Unicode→HChar 문자표를 읽습니다. 일반 Johab 코드로 특수문자를 잘못 조회하던 경로를 제거했습니다. HCI Poppy·Hollyhock의 보통 영문 외곽선도 지원하며, PDF 기준 1000/em 좌표·글자 폭은 절삭합니다. HWP/HWPX의 4개 서체에서 **108개 글자 경로와 절삭 글자 폭**이 한컴 PDF Type3와 일치했고, 생성한 CFF 글자 폭도 대조했습니다. 빈 글리프의 0 폭과 원래 공백 폭을 유지합니다. 전체 글꼴·힌팅·스타일·문서 동일성 검증은 아닙니다.

누락된 글꼴은 설치된 한국어 FontDB의 기본 대체 순서를 따릅니다. 시험 문서의 누락된 명조·고딕 이름 모두 한컴과 같은 한컴바탕으로 선택됐습니다. 문자별 대체와 사용자 정의 글꼴 대체까지 전부 복원한 것은 아닙니다. 설치 글꼴·문자표·변환 캐시는 배포하지 않습니다.

## PDF 투명도 점무늬와 비트맵 글꼴 추가 검증

불투명 RGB/RGBA 그림의 PDF 경로에 300 dpi 8×8 흰 스텐실을 구현했습니다. alpha 0~3은 불투명, 252~255는 그림을 생략하고 4~251은 단계별 무늬를 씁니다. HWP/HWPX의 256단계와 12개 반복 값, 총 **520개 중간 단계 마스크 바이트**가 한컴과 일치했습니다. 나래 PDF 안의 실제 마스크도 검사했습니다. 한컴의 초기 무늬 위치는 재사용된 프로세스의 앞선 출력에 영향을 받아 시험마다 첫 마스크에서 확인했습니다. 나래는 출력 재현성을 위해 0부터 시작하고, 알 수 없는 한컴 초기 상태와 프린터 좌표·원본 알파·회전의 남은 차이를 진단합니다. 쪽 전체 일치 판정에는 위치 보정을 적용하지 않습니다.

명조·고딕은 설치 HFT의 가장 큰 비트맵 크기를 읽습니다. 600 dpi 정수 em과 원래 em 좌표에서 각 픽셀 경계를 버리는 규칙으로 확대하고, 독립 PDF에 별도 글자 이미지로 넣습니다. 8가지 크기, 한글·영문·한자 표본의 **208개 비트맵 글자 마스크**가 한컴과 픽셀까지 같고 나래 PDF에 들어간 마스크도 같습니다. 비교는 글자 이미지의 잉크 영역에 한정하며 크기 조절을 하지 않았습니다. 한컴의 버퍼 여백·글자 위치·스타일·전체 문서 일치가 아닙니다. 고딕의 설치 설정에 없는 한자 얼굴은 미지원 문자 대체로 진단하며 이 208개에 포함하지 않습니다.

REA로 `HncBaseDraw.dll`의 `0x100ac080` 문자 매핑, `0x100ac550` 비트맵 조합·행 정렬, `0x10062690/0x10062740` 그리기 버퍼를 확인했습니다. ## 자간·기울임·줄 높이와 채우기 추가 검증

HWP 제어 문자의 UTF16 위치는 유지하면서 U+200B에 가짜 자간이 더해지지 않도록 했습니다. 자간은 모든 글자에 em 기준 고정 폭을 더하던 계산에서 글자별 폭에 대한 비율로 수정했습니다. 일반 공백도 반 em 폭에 같은 비율을 적용하고 인라인 개체의 명시한 폭은 보존합니다. 실제 한컴의 영문·한글·공백 출력에서 이 비율을 확인했지만 600 dpi 정수 폭의 누적과 조정값은 아직 완전히 복원하지 못했습니다.

REA의 PDF 드라이버 `0x100189f0/0x10019420/0x1001ca00`에서 기울임 플래그, 실제 Italic 얼굴의 합성 제외, 0.333333 기울임을 확인했습니다. 나래의 외곽선과 명조 비트맵에 기준선 중심의 합성 기울임을 적용하고 실제 Italic 얼굴을 유지합니다. HWP/HWPX의 5개 서체·보통/기울임, 총 20쪽 표본에서 한컴 변환 행렬과 나래 PDF에 실제 들어간 경로·비트맵 변환을 검사했습니다. 글자별 자동 대체, PDF 수치 정밀도·힌팅·전체 쪽 일치는 남아 있습니다.

한컴 포함 관련 검사 **46개가 새 순차 실행에서 모두 통과**했고, 한컴을 끈 전체 검사는 67개 중 39개 통과·28개 건너뜀입니다. 실제 7개 파일·124쪽을 새로 독립 출력해 원본 해시와 쪽수를 유지했습니다. trip-hwpx의 쪽별 최대 변경 픽셀 비율은 11.20%에서 6.52%로 줄었습니다. 독립-한컴 전체 문서는 여전히 0/7개, 쪽은 2/124쪽 일치입니다. 비교의 허용 오차·크기·좌표 보정은 바꾸지 않았습니다.

## 압축 전 RGB555 사진 관찰

REA Frida로 작업 사본을 연 소유 한컴 프로세스의 PDF 비트맵 분기를 읽기 관찰했습니다. 두 불투명 BMP 사진의 압축 전 304×190 비트맵은 RGB555(채널별 5비트 확장값)였고 색상 수가 각각 1,135·903개였습니다. 첫 그림은 자동 JPEG 품질이 74에서 51로 내려갔고 둘째는 74를 유지했습니다. 정적 분석의 색상 수 1,024개 분기와 부합합니다.

캡처한 두 압축 전 비트맵을 Pillow JPEG의 해당 품질·4:2:0으로 인코딩하면 한컴 PDF 사진과 **복호한 RGB 픽셀이 모두 같습니다.** JPEG 바이트열은 같지 않습니다. 이 일치는 캡처 비트맵을 사용한 인코더 표본 검사이며, 나래가 원본 사진에서 같은 비트맵을 생성했다는 뜻이 아닙니다. 이 관찰 당시에는 RGB555 변환을 축소 앞뒤에 넣은 Pillow와 GDI 시험에도 차이가 남았습니다. 이어지는 작업에서 아래와 같이 GDI+ 32비트 축소와 별도의 4×4 색상 점무늬를 구현했습니다.

관찰을 붙인 출력은 중간에 `PrintToPDFEx` COM 예외로 중단됐습니다. 그 부분 PDF는 모든 일치 검사에서 제외했습니다. 관찰을 해제하고 다시 정상 출력한 같은 문서의 24쪽을 사용해 위 JPEG를 대조했으며 원본 해시는 유지됐습니다. Frida 세션과 작업 문서는 닫았습니다. 관찰한 문서·비트맵·부분 PDF·원시 메시지는 로컬에만 보관하며 저장소에는 근거 ID·해시와 위 수치만 기록합니다.

## PDF 그림 축소·색상 점무늬·프린터 배치 구현

일반 불투명 RGB BMP/PNG와 알파가 모두 255인 RGBA PNG의 무효과·무회전·전체 그림 경로를 구현했습니다. 최대 96 dpi로 축소하며 확대는 하지 않습니다. REA의 실제 호출 관찰에서 GDI+ 원본 픽셀 해시·대상 비트맵·보간 모드·페이지 단위를 확인했습니다. `HncBaseDraw::_SaveBitmapPlus`의 첫 축소 대상은 32비트였고 RGB555는 뒤 단계였습니다. GDI+ 64비트는 촘촘한 시험 무늬에서 32비트와 1~2채널 값이 달랐습니다. 자체 C# 소스를 x86으로 빌드해 Windows GDI+만 호출하며 한컴 DLL은 로드하지 않습니다. .NET Framework 4 x86 컴파일러가 없으면 기존 경로와 사유를 기록합니다. 빌드 결과는 사용자 캐시에만 두고 소스만 배포합니다.

축소 뒤 RGB555 변환은 4×4 순위와 비트맵의 아래쪽 행을 기준으로 하는 색상 점무늬를 씁니다. 투명도 8×8 점무늬와는 별개입니다. 색상 수와 그림의 실제 프린터 폭으로 자동 JPEG 품질을 계산하고, JPEG를 복호한 픽셀을 Qt PDF에 추가 손실 없이 넣습니다. 실제 문서 사진 **8개의 독립 PDF 이미지 픽셀**이 한컴 JPEG의 복호 픽셀과 정확히 같습니다. 저장 형식과 JPEG 바이트열이 같다는 뜻은 아닙니다.

그림 위치·크기는 600 dpi 정수 격자, EMF 용지 배율의 단정밀도 계산, PDF 그림 행렬의 소수 셋째 자리로 변환합니다. 클립은 그림 크기와 독립적으로 양쪽 모서리를 반올림합니다. 153.90pt처럼 정확한 절반 픽셀을 이진 부동소수점 때문에 잘못 반올림하지 않도록 HWPUNIT의 절반 단위 정수로 계산합니다. 실제 사진 **8개의 그림 행렬**도 한컴과 같습니다. 비교 결과를 이동·정렬한 것이 아니라 원본 조판을 그릴 때 적용하는 프린터 좌표 규칙입니다.

BMP·RGB PNG·불투명 RGBA PNG, 두 크기의 HWP/HWPX 시험 문서 **12쪽 모두 쪽 크기와 RGB 픽셀이 전체 쪽에서 같습니다.** 이 시험의 DPI는 96, 허용 오차는 0이고 크기 조절·좌표 정렬을 하지 않았습니다. 사진이 많은 실제 보고서 13쪽의 변경 픽셀 비율은 49.19%에서 2.82%로, 보고서 전체의 쪽별 최대는 23.59%로 줄었습니다. 실제 검증 문서 전체는 여전히 0/7개, 쪽은 2/124쪽 일치입니다.

한컴 포함 관련 검사 **51개가 순차 실행에서 모두 통과**했습니다. 한컴을 끈 전체 검사에서는 72개 중 43개 통과·29개 건너뜀이며, 새 캐시를 공유한 보조 프로그램 4개 동시 실행도 같은 네이티브 표본 해시를 반환했습니다. 기존의 520개 투명도 마스크·208개 비트맵 글자·108개 외곽선·14,848개 PNG 색상 표본 검사도 이 실행에 포함됩니다. 설치한 스킬 CLI와 7개 실제 문서 124쪽의 출력·원본 해시·쪽수를 다시 확인했습니다.

JPEG 원본·색인 이미지, 원본 알파·그림 alpha·효과·잘라내기·반전·회전은 기존 경로로 남으며 `layout.pdf_bitmaps`에서 확인합니다. `prepared`는 새 처리를 수행했다는 뜻이며 전체 일치가 아닙니다. 이 단계에 남아 있던 일부 비확대 픽셀 차이와 같은 그림의 첫 JPEG 품질 재사용은 아래 후속 작업에서 해결했습니다. 추가 Frida 관찰용 문서는 정상 출력됐고 세션·작업 문서를 닫았으며, 정적 분석 스냅샷과 설치 바이너리 해시는 유지됐습니다. 개인 문서·캡처 비트맵·원시 Frida 메시지·디컴파일·컴파일 결과는 저장소에 넣지 않습니다.

## JPEG·팔레트·회색조와 홀수 열 추가 구현

REA Frida로 합성 문서의 원본·축소 대상 픽셀, GDI+ 중간 저장 파일, PDF 압축 전 RGB와 품질을 읽기 관찰했습니다. JPEG는 최대 500 dpi로 축소한 뒤 GDI+의 기본 JPEG로 중간 저장되고, GIF는 축소할 때 GDI+ GIF 팔레트로 저장됩니다. 원래 크기의 GIF는 기존 팔레트를 유지합니다. 중간 결과를 생략했던 JPEG/GIF 차이를 이 경로로 해결했습니다. 8비트 회색조는 RGB555로 줄이지 않습니다. 관찰한 8개 압축 전 비트맵도 재현했습니다.

JPEG 계수 차이로 추정했던 작은 오차는 압축 전 RGB555의 마지막 열에서 생겼습니다. 폭이 4n+1일 때 마지막 픽셀에 순위표의 세 번째 열을 적용합니다. 폭 63·65·67·129·257과 캡처된 193·257 픽셀로 대조했고 JPEG 복호 픽셀도 같습니다. 같은 픽셀과 크기로 PDF 이미지를 재사용할 때 처음 정한 JPEG 품질을 유지하도록 출력별 캐시도 추가했습니다. 이것으로 작은 크기의 JPEG와 큰 크기의 JPEG가 같은 비트맵을 공유하는 경우를 맞췄습니다.

JPEG 축소·원본 크기·크기별 품질 재사용, GIF 축소·원래 팔레트, RGB BMP 홀수 폭, 팔레트 PNG/BMP, 회색조 PNG/JPEG를 HWP/HWPX로 검사한 **추가 32쪽이 전체 일치**합니다. 앞선 BMP/PNG 12쪽을 포함한 **합성 44쪽 전체**가 같은 용지 크기·96 dpi RGB 픽셀·허용 오차 0으로 같으며, 크기 조절·좌표 정렬을 하지 않았습니다. 실제 사진 8개의 PDF 픽셀도 다시 일치했습니다. 이는 검사한 표본의 결과입니다.

관련 한컴 포함 검사 52개를 5개 모듈로 순차 실행해 모두 통과했고, 한컴을 끈 전체 검사 73개 중 43개 통과·30개 건너뜀입니다. 새 보조 프로그램 캐시의 4개 동시 실행, 설치 스킬 CLI와 스킬 검사도 통과했습니다. 실제 7개 문서 124쪽의 원본 해시·쪽수는 유지했고 trip-hwpx의 최대 변경 픽셀 비율은 6.52%에서 5.85%로 줄었습니다. 실제 문서 전체 일치는 0/7개, 쪽별 일치는 2/124쪽으로 전체 목표는 미달성입니다.

원본 알파·그림 alpha·효과·잘라내기·반전·회전, 다른 형식과 비율의 미검증 경우, 투명도 시작 상태·글꼴·표·페이지 경계는 계속 조사합니다. `layout.pdf_bitmaps`는 그림의 처리 범위·해상도·중간 저장·회색조/팔레트·품질 재사용을 기록합니다. 작업 문서와 Frida 세션을 닫고 근거 묶음을 로컬에 저장했으며 설치 바이너리의 SHA256은 유지됐습니다. 원시 근거와 중간 그림은 배포하지 않습니다.

## 비트맵 문장 전체 쪽과 작은 글자 추가 검증

앞선 208개 글자 마스크 검사를 **동일 208쪽의 전체 RGB 픽셀 검사로 보강**했습니다. 글자마다 잉크만 잘라 넣던 경로를 한컴의 전체 텍스트 버퍼로 바꾸고 버퍼의 흰 여백·가드 픽셀·위치를 포함했습니다. 문자 종류와 단어 경계에서 버퍼를 나누고, 85% ascent 기반 높이·가로 여백·16비트 행 정렬·2047픽셀 및 63,488바이트 분할을 반영합니다. 마지막 세로 조각의 가드 행도 재사용된 비트맵의 내용을 유지합니다.

REA 정적 분석에서 `HncBaseDraw.dll`의 버퍼 생성·BitBlt와 논리 간격 변환, `HNCE2PTP.dll`의 EMF 비트맵 재생을 확인했습니다. 별도로 합성 문서를 출력하는 Frida 관찰에서 7200→600 정수 변환 전후의 실제 위치·간격 배열을 확인했습니다. 글자 폭은 4 HWPUNIT으로 반올림한 뒤 자간을 적용하고 다시 반올림합니다. 기본 반 em 공백은 버림하고 문단 마지막 글자에는 자간을 더하지 않습니다. 버퍼가 바뀌어도 누적 논리 위치에서 계산해 기기 반올림 위상을 유지합니다. −7%에서 드러난 두 단계 반올림 차이도 포함합니다.

## 보통 글꼴 PDF·조합 외곽선과 논리 배치 추가 검증

Qt의 PDF 부분 글꼴이 생략하던 TrueType 힌팅 프로그램을 설치 원본에서 보존하고, 글리프 경계와 head 플래그도 재계산하지 않도록 했습니다. TTF/TTC는 Qt의 실제 head/maxp/name 표와 설치 파일을 대조합니다. HFT는 원본 외곽선을 Type3로 넣고 한양 신명조·중고딕의 누락된 한글에는 휴먼명조·고딕의 조합 외곽선을 적용합니다. 512단위 Human 글꼴은 기준선부터 원본 정수 단위로 반올림합니다. 설치 FontDB의 Hanja 대체 순서도 구분해 읽습니다.

같은 얼굴의 한글·영문·한자 파일은 256코드 PDF 캐시를 공유하고, 자간 보정·대체 전환과 코드 경계에서 원래의 프린터 위상을 유지합니다. 8pt 글자를 먼저 67프린터 픽셀로 반올림해 한 줄에 한 글자씩 덜 넣던 줄바꿈도 논리 폭으로 수정했습니다. 기준선은 문단 원점에 누적 줄 위치를 더해 계산합니다. 도형·채운 셀이 남긴 PDF 숫자 정밀도는 다음 쪽까지 이어갑니다. 보이는 글꼴은 Unicode를 중복 반환하지 않으며 기존 의미 텍스트층을 보존합니다.

HWP/HWPX 각각 101쪽, 총 **202쪽이 용지 크기와 전체 RGB 픽셀까지 일치**했습니다. 11개 보통 TTF/TTC/HFT 얼굴, 5~18pt, 색·자간·정렬·공백 설정·혼합 얼굴, 조합 한글 260글자, 같은 HFT의 300글자와 256코드 경계를 포함합니다. 텍스트도 전 쪽 대조했습니다. 정밀도 시험은 4쪽 중 다음 쪽의 텍스트 전용 2쪽이 전체 일치했고, 첫 쪽 표 배치에는 형식별 2,902픽셀 차이가 남습니다.

새 한컴 기준 출력에서 일부 글자 간격이 1프린터 픽셀 달라지는 원인은 인쇄 전에 읽던 PageCount였습니다. 같은 101쪽 입력에서 미리 조회하면 96쪽 일치, 인쇄부터 하면 101쪽 일치를 확인했습니다. 기준 경로는 PrintToPDFEx 이후 최종 쪽수만 읽고 관찰하지 않은 인쇄 전 값은 null로 남깁니다. 앞선 기준 PDF는 변경하지 않았습니다.

뷰어 관련 **58개 검사가 각각 최종 통과**했습니다. 묶음 재실행은 Windows 메모리 부족으로 중단돼 완료된 29개 통과만 세고, 남은 검사는 빈 비표시 자동화 서버 정리 후 두 묶음으로 나누어 재검증했습니다. 58개 전체가 한 번에 통과한 것으로 보고하지 않습니다. 한컴을 끈 전체 검사는 79개 중 46개 통과·33개 건너뜀입니다. 앞선 전체 78개 실행은 글꼴 기준 출력 실패 1개·한컴 그림 편집 저장 검증 오류 1개가 있어 전체 통과로 보고하지 않습니다. 인쇄 순서를 고친 새 글꼴 검사 4개와 메모리 정리 후 그림 편집 검사 1개는 통과했고, 편집 코드는 바꾸지 않았습니다. 설치 스킬의 24쪽 형식 쌍 비교와 29쪽 읽기도 통과했습니다.

실제 7개·124쪽은 원본 해시와 쪽수를 유지했고 **0/7개 문서·4/124쪽 일치**입니다. 보고서 두 형식은 각각 5쪽 한 쪽이 일치하며 최대 변경 비율은 23.58%에서 18.06%로 줄었습니다. trip-hwpx는 5.85%에서 5.21%, minutes-hwpx는 12.27%에서 11.37%로 줄었지만 form-hwp는 최대 15.50%에서 15.64%로 소폭 늘었습니다. 미지원 스타일·배분 정렬·표·개체 배치와 투명도 초기 상태 등이 남아 전체 무차이 목표는 계속 미달성입니다. 비교 DPI 96, 허용 오차 0, 크기·좌표 보정 없음은 유지했습니다.

REA의 PDF 숫자 정밀도와 HFT 논리 폭·조합 색인·외곽선 해독을 추가 조사하고 스냅샷을 저장한 뒤 세션을 닫았습니다. 설치 DLL 해시는 유지됐고 문서·글꼴·바이너리·원시 분석 자료는 배포하지 않습니다.

## 예전 HWP 가운데선 해석 수정

HWP 글자 모양의 밑줄 종류 2를 밑줄과 함께 표시하던 해석을 수정했습니다. 한컴의 HWPML과 단독 출력 시험에서 이 값은 예전 취소선 표현으로 확인됐습니다. 종류 1·3은 밑줄, 종류 2는 취소선으로 읽습니다. 밑줄·취소선을 수정할 때는 예전 표현을 현재 취소선 비트로 정규화하고, 다른 편집은 원래 표현을 유지합니다.

예전 HWP·현재 HWP·재생성 HWPX의 한컴 출력끼리 전체 쪽이 같았고 독립 출력끼리도 같았습니다. 이 관계 검사는 독립-한컴 스타일 전체 일치의 증명이 아닙니다. 원본 보존 편집 3개 경우를 포함한 새 검사 3개가 통과했고, 한컴을 끈 전체 검사는 82개 중 48개 통과·34개 건너뜀입니다. 이전 글꼴·뷰어 58개와 합쳐 61개의 최종 통과를 기록하되 한 번의 전체 통과로 보고하지 않습니다.

실제 7개·124쪽을 다시 출력해 원본 해시·쪽수를 유지했습니다. 안내서의 변경 픽셀 합은 5,143,869에서 4,573,882로 11.08% 줄고 최대 변경 비율은 23.33%에서 21.66%로 줄었습니다. lesson-hwp의 최대 비율도 25.00%에서 23.52%로 줄었습니다. 전체 일치는 여전히 0/7개 문서·4/124쪽입니다.

추가 시험에서 한컴이 취소선 모양 13~15를 표시하지 않는 동작도 확인했습니다. 나래는 아직 모양을 구분하지 않고 실선으로 표시해 이 차이가 남습니다. 취소선 모양·색, 위 밑줄, 다른 스타일과 표·배치 차이는 후속 작업입니다.

## 취소선 모양·색 보존과 표시하지 않는 모양

취소선의 모양과 색을 HWP/HWPX 모델·재생성·원본 보존 편집에 유지합니다. 예전 HWP 가운데선 종류 2는 현재 취소선 비트도 켜져 있어도 밑줄 필드의 모양·색을 사용합니다. 밑줄을 추가하는 등 표현을 정규화할 때 두 값을 현재 취소선 필드로 옮기고, 오래된 편집 세션이 모르는 필드는 다른 편집으로 바꾸지 않습니다. 한컴의 직접 형식 변환으로 16종을 확인해 `DOT`·`DASH` 순서와 `DOUBLEWAVE`·3D 계열 이름도 맞췄습니다.

`THICK3D`·`THICKREV3D`·`3D`는 한컴처럼 선을 그리지 않고 원래 글자를 표시합니다. 6개 TTF/TTC/HFT 얼굴·5/13pt·다른 글자/취소선 색·세 모양을 두 형식으로 검사한 **72쪽 전체**가 한컴과 일치합니다. 취소선 없는 한컴 출력도 함께 대조했습니다. `layout.pdf_native_text.suppressed_strike_glyphs`는 이 경로의 처리 수로, 전체 일치 판정은 아닙니다. 보통 글꼴 202쪽도 다시 전체 일치했고 정밀도 표 시험 첫 쪽의 2,902픽셀 차이는 유지됩니다.

새 관련 검사 9개가 한 묶음으로 통과했습니다. 앞선 관련 58개와 합친 67개는 서로 다른 시점의 최종 통과이며 전체를 한 번에 실행한 결과가 아닙니다. 한컴을 끈 전체 검사는 88개 중 52개 통과·36개 건너뜀입니다. 설치 스킬의 24쪽 형식 쌍 비교와 29쪽 읽기도 다시 확인했습니다.

모든 모양의 한컴 HWP/HWPX 출력끼리 같다고 가정했던 추가 시험은 16쪽 중 5쪽에서 각각 103픽셀 차이로 실패했습니다. 마지막 숫자 앞 간격이 1프린터 픽셀 달랐고 별도 저장한 쌍에서도 재현됐습니다. 이 시험은 형식 변환의 모양·색 보존을 검사하도록 범위를 바로잡았으며, 한컴의 조판 상태에 따른 출력 차이는 해결하지 않았습니다. 빈 비표시 자동화 서버 정리 전의 한컴 상호 비교 실패와 RGB 대소문자를 다르게 비교했던 시험 실패 기록도 보존합니다. 모든 한컴 실행 상태에서 같다는 주장은 하지 않습니다.

실제 7개·124쪽은 원본 해시·쪽수를 유지했고 전체 일치는 여전히 **0/7개 문서·4/124쪽**입니다. 안내서의 변경 픽셀 합은 직전 4,573,882에서 3,973,302로 13.13% 줄고 최대 변경 비율은 21.66%에서 20.75%로 줄었습니다. 새 글꼴 경로로 처리하는 줄은 9줄에서 1,017줄로 늘었습니다. lesson-hwp 최대 비율은 23.52%에서 22.71%로 줄었습니다. 다른 실제 파일의 비율은 직전과 같습니다.

REA Frida의 GDI 추적은 11개 훅의 준비만 관찰했고 `PrintToPDFEx`의 StartDoc/EndDoc 작업은 잡지 못했습니다. 이 기록을 취소선 위치의 증명으로 사용하지 않습니다. 위 동작은 한컴 형식 변환과 직접 전체 쪽 출력으로 검증했습니다. 세션·작업 문서·REA 서버를 닫았고 설치 DLL 해시는 유지됐습니다. 표시하는 취소선의 위치·무늬, 위 밑줄, 다른 스타일·배분 정렬·표·쪽 경계 차이는 계속 남습니다.

## 글자처럼 배치한 표의 간격과 HWPX 여백 단위

저장된 줄 좌표 없이 커진 인라인 표·도형 뒤에서 문단의 줄 간격이 사라지던 문제를 수정했습니다. `affectLineSpacing`을 끄면 원래 글자 줄의 간격을 유지하고, 켠 백분율 간격은 커진 개체 높이를 기준으로 계산합니다. 다른 간격 종류·인라인 그림·복잡한 쪽 나눔의 모든 동작을 복원한 것은 아닙니다.

단순 HWPX의 문단 여백을 버전별 default와 같은 배율로 쓰던 오류도 수정했습니다. 직접 속성과 HwpUnitChar case는 100단위/pt, 버전별 default는 200단위/pt입니다. 한컴으로 다시 저장한 문서를 읽어 확인했고 다섯 여백 필드의 원본 보존 편집도 같은 의미를 유지합니다. 기존 한컴 실제 HWPX 세 파일은 모두 버전별 속성이므로 이 단위 변경으로 여백을 바꾸지 않습니다.

`affectLineSpacing` 두 값·100/150/160/200%·문단 뒤 0/3pt를 두 형식으로 출력한 **32쪽 전체가 한컴과 일치**합니다. 새 관련 검사 3개가 통과했고 한컴을 끈 전체 검사는 91개 중 53개 통과·38개 건너뜀입니다. 앞선 관련 검사와 누적한 70개는 서로 다른 시점의 최종 통과입니다. 처음 새 검사가 서로 다른 기본 테두리를 함께 비교하고 전체 문단 스타일을 대체해 실패했던 기록도 보존하며, 검사는 요청한 여백 필드만 수정·대조하도록 바로잡았습니다.

실제 7개·124쪽은 원본 해시·쪽수를 유지했습니다. trip-hwpx의 전체 차이 픽셀은 64,425에서 47,077로 26.93% 줄고 쪽별 최대 비율은 5.21%에서 4.81%로 줄었습니다. 둘째 쪽 차이는 18,010에서 4,204픽셀로 줄었습니다. 다른 실제 파일의 비율은 직전과 같고 전체 일치는 여전히 **0/7개 문서·4/124쪽**입니다. 보통 글꼴 202쪽도 재검사해 일치했으며 정밀도 표 시험 첫 쪽의 남은 차이는 각 형식 2,902에서 2,002픽셀로 줄었습니다. 전체 무차이 목표는 미달성입니다.

## 장평·공백 폭과 PDF 글자 간격 보정

TTF/TTC는 요청한 폭을 논리 글자 크기로 정수화하고, 반올림한 프린터 em의 평균 폭과 나누어 PDF 가로 배율을 만듭니다. HFT는 요청 비율을 사용합니다. 공백·느낌표는 기본 반 글자 폭을 먼저 4단위에 맞춘 뒤 장평·자간을 적용합니다. PDF는 가로 배율을 적용하기 전의 자연 폭과 출력 간격이 같은지 먼저 비교해 보정을 생략하는 한컴 분기도 따릅니다. 정렬 폭에서는 끝의 ASCII 공백을 제외합니다. `stretched_glyphs`는 처리 수이며 일치 판정이 아닙니다.

7개 서체·5/11/13/18pt·장평 50/95/105/150%와 자간 -16/16·가운데/오른쪽 정렬·글꼴 공백의 조합을 두 형식으로 새로 출력했습니다. HWP/HWPX 각각 176쪽, **총 352쪽의 용지 크기·전체 RGB 픽셀·텍스트가 일치**합니다. DPI 96·오차 0이며 좌표나 크기를 맞추지 않았습니다. 보통 글꼴 202쪽도 다시 일치했습니다. 한컴을 끈 전체 검사는 92개 중 53개 통과·39개 건너뜀이며, 새 한컴 포함 검사 1개가 두 형식 352쪽을 검사합니다. 앞선 검사와 누적한 71개는 서로 다른 시점의 최종 통과입니다. 설치 CLI의 24쪽 형식 쌍과 29쪽 읽기·설치 스킬 검사도 확인했습니다.

끝 공백이 있는 정렬을 추가로 검사한 HWP 12쪽 중 10쪽은 일치하지만, 함초롬바탕 13pt 오른쪽 정렬의 장평 100/105% 두 경우는 209/104픽셀 차이가 남습니다. 한 쪽짜리 새 입력으로도 209픽셀 차이가 재현됩니다. REA로 읽은 정렬 상자 폭은 같았고 일부 글자의 한컴 논리 폭이 원본 hmtx와 조금 달랐습니다. 이 두 경우·다른 문자 조합·다른 DPI까지 검증한 것으로 확대하지 않습니다.

실제 7개·124쪽의 원본 해시·쪽수는 유지했고 전체 일치는 여전히 **0/7개 문서·4/124쪽**입니다. trip-hwpx의 차이 픽셀은 직전 47,077에서 26,960으로 줄고 최대 비율은 4.81%에서 2.55%로 줄었습니다. 안내서는 3,973,302에서 3,941,770, minutes-hwpx는 188,077에서 180,056픽셀로 줄었습니다. 반면 lesson-hwp의 총 차이는 933,646에서 937,951픽셀로 늘었고, form-hwp의 최대 비율도 소폭 늘었습니다. 모든 지표가 개선되었다고 보고하지 않습니다.

REA의 읽기 추적에서 TTF 평균 폭·요청 폭, 7200단위 논리 간격과 600 dpi 출력 간격을 대조했습니다. 추적한 112쪽 한컴 PDF는 관찰하지 않은 기준 PDF와 모두 같았습니다. 기존 PDF 글자 출력 분석도 재확인했습니다. TTF 경로에서 호출되지 않은 글꼴 폭 훅은 준비 상태만 기록했으며 측정 경로의 증명으로 쓰지 않습니다. 모든 작업 문서·Frida 세션·REA 서버를 닫고 설치 DLL 해시를 확인했습니다. 원시 추적·문서·글꼴·바이너리는 배포하지 않습니다.

소스 해시는 Git 배포와 같은 LF로 줄바꿈을 정규화해 기록합니다. Windows 작업 사본의 CRLF 차이 때문에 앞선 ZIP과 검증 소스 해시가 달랐던 부분을 바로잡고, 배포 ZIP의 소스 바이트와 함께 확인합니다.

## REA 분석

[REA](https://github.com/morluto/rea) 6.5.0과 로컬 Ghidra 12.1.4로 설치된 `HwpAutomation.dll`, `HwpApp.dll`을 분석했습니다. `PrintInfo/PrintMethod`와 `hp:linesegarray`, `vertpos/vertsize/textheight/baseline/spacing/horzpos/horzsize`의 읽기 경로를 실제 디컴파일·참조 조사로 확인했습니다. 관련 함수는 `0x10477da0`, `0x1063cd60`, `0x1063c980`이며 한컴 전체 재조판 알고리즘의 복원은 아닙니다.

캐시 문단 좌표와 새 문단 흐름을 섞으면 안 된다는 판단은 이 정적 분석과 실제 HWPX의 3쪽/2쪽 재현을 함께 근거로 한 구현 판단입니다. 한컴의 모든 동작을 정적 분석으로 증명했다고 주장하지 않습니다. 두 바이너리의 분석 전후 SHA256이 같고 세션을 닫았습니다. 근거 식별자와 소스 해시는 [validation.json](validation.json)에 있습니다. 원본 문서·PDF·쪽 이미지·한컴 바이너리·글꼴·원시 디컴파일은 저장소에 포함하지 않습니다.

추가 그림 분석에서는 `0x10634330`의 `imgClip/flip/rotationInfo` 태그별 생성 경로와 `0x10623720`의 밝기·대비 정수, alpha 실수 읽기를 확인했습니다. 이는 XML 입력 경로 조사이며 반전 순서는 한컴에서 만든 시험 파일의 실제 출력으로 검증했습니다. `HncPdfSdk.dll`도 조사했으나 PDF 그림의 정확한 압축·다운샘플 수식은 복원하지 못했습니다. 추가 세션을 닫았고 설치 바이너리의 해시가 유지됐습니다.

`HncBaseDraw.dll`의 채널 변환 `0x1000b070`과 RGBA 처리 `0x10065ce0`에서 밝기·대비·투명도 계산을 확인했습니다. HFT 글자 폭 경로 `0x10074ee0`, 로더 `0x100ab220/0x100abc00`, `HncFoundation.dll`의 Unicode→HChar와 문자표 로딩 `0x10061d30/0x1005db70/0x1005c280`도 조사했습니다. 이 정적 근거와 별도의 실제 출력 표본을 함께 사용했습니다. REA 세션은 닫았고 설치 바이너리 해시가 유지됐습니다.

## 검사와 남은 차이

앞선 변경의 뷰어·그림·글꼴 검사 35개는 실제 한컴을 켠 새 순차 실행에서 모두 통과했습니다. 한컴을 끈 전체 검사에서는 56개 중 32개가 통과했고 한컴 의존 24개를 건너뛰었습니다. 이전 커밋의 전체 한컴 포함 48개 통과 기록은 보존했습니다. 이번 전체 한컴 재실행 시도는 COM 서버 실행 오류와 중단으로 완료되지 않았으며 통과로 집계하지 않습니다. 좌우·상하 모두 비대칭인 잘라내기 조건으로 보강한 2개 검사도 실제 한컴을 포함해 추가 통과했습니다. 스킬 검증과 설치한 스킬의 실제 CLI도 통과했습니다. 이전 편집기의 추가 배치 검사 19개 중 18개가 통과했고, 남은 한 개의 구형 커서 폭 임계값 검사는 기존 main과 수정본에서 동일한 값으로 실패합니다. 이 외부 구형 검사를 통과했다고 보고하지 않습니다.

독립 출력에는 HFT 비트맵의 위치·스타일·다른 서체, 미지원 문자·힌팅·서체 대체, 표·개체 세부 표현, 그림 압축·다운샘플 차이가 남습니다. 불투명 BMP/PNG/JPEG/GIF의 RGB·팔레트·회색조 경로는 앞서 설명한 추가 작업에서 구현했지만 원본 알파·그림 alpha·효과·잘라내기·반전·회전과 다른 형식·비율·인코딩의 미검증 경우는 남습니다. 그림의 쪽과 위치가 비슷해도 이를 무차이라고 판단하지 않습니다. 정확한 한컴 조판 확인은 `--backend hancom`을 명시하고, 독립 엔진 개선 확인은 `verify --hancom`으로 계속 검사합니다.

## 표 격자·셀 원점과 HWPX 테두리 두께

셀 위치를 부모 원점에서 프린터 단위로 누적하고, 글자 위치도 그 논리 원점을 유지합니다. 한 셀씩 사각형 네 변을 겹쳐 그리던 출력은 지원 범위에서 공유 세로·가로 선으로 바뀝니다. 평평한 선 끝, 홀수 프린터 픽셀 두께의 좌우 비대칭 연장, 내용 뒤에 반복되는 바깥 경계선을 반영합니다. 표 자체 borderFill의 선은 셀 선을 덮어쓰지 않는 것도 실제 한컴 출력으로 확인했습니다.

본문에 글자처럼 배치한 한 쪽짜리 비병합 직사각형 격자와 동일한 SOLID/NONE 셀 테두리를 우선 지원합니다. Arial 13pt·1/2행·1/2/3열·분수 너비/높이/안쪽 여백·좌/중앙/우 정렬·위/중앙 세로 정렬·불투명 채우기·선 두께와 색 조합이 HWP/HWPX 각각 44쪽, **88쪽 전체 일치**했습니다. 이전에 첫 쪽 2,002픽셀 차이가 남던 정밀도 표본도 두 형식의 두 쪽씩 **4쪽 전체 일치**합니다. DPI 96·RGB 오차 0이며 용지와 좌표를 맞추지 않았습니다. 병합·쪽 나눔·떠 있는 표·중첩 표·혼합 테두리·다른 DPI/글꼴/조판 문맥까지 검증한 결과는 아닙니다.

실제 로고는 원본 바이트가 GIF였습니다. 탐색 중 사본을 `source.png`라는 이름으로 저장했지만 PNG 구현의 근거로 사용하지 않습니다. 투명 GIF는 원래 픽셀 크기의 첫 프레임을 유지하고 RGB와 역 알파 1비트 PDF ImageMask를 따로 출력합니다. 투명한 팔레트 색은 흰 바탕으로 바꾼 뒤 색 수를 세며 255색 이하는 원래 색, 256색은 기존 RGB555 변환을 씁니다. 같은 이미지라도 배치 크기에 맞게 JPEG 품질을 각각 고릅니다. 확대 배치가 앞선 작은 배치의 품질을 재사용하지 않습니다.

## 비율 줄 간격의 정밀도와 첫 실제 문서 전체 일치

실제 `trip-hwpx`의 첫 쪽에 남은 4픽셀은 글리프나 로고가 아니라 앞선 문단의 줄 간격에서 시작됐습니다. 한컴의 작업 사본을 인쇄하고 다시 저장해 줄 배치를 읽으니 11pt·150% 문단은 줄 사이 간격 5.52pt, 줄 진행 16.52pt였습니다. 기존 5.50/16.50pt가 네 줄 뒤 표 경계를 옮겨 글자 끝을 잘랐습니다. 같은 문서의 한컴 반복 PDF도 보존한 원래 기준과 2/2쪽 전체가 일치했습니다. 이 자료는 한컴의 줄 배치/PDF 대조에서 얻었으며 새 내부 함수를 REA로 추적했다는 주장은 하지 않습니다.

비율 간격 계산에서는 선언된 글자 높이를 유지하면서 간격 계산용 높이를 먼저 4 HWPUNIT로 버립니다. 그 높이에서 `(비율-100)%`의 간격을 계산하고 간격만 따로 4단위로 반올림합니다. 음수 절반도 0에서 먼 쪽으로 반올림합니다. 소수점 글자 높이와 비율 42개의 한컴 배치에서 이 순서를 확인했습니다. 100% 미만에서는 음수 간격을 보존하며, 0%의 같은 위치에 겹친 줄은 같은 쪽에 남깁니다. 계산 중 실제 쪽 넘침을 표시해 저장된 줄의 절대 좌표와 구분합니다.

새 `test_percent_line_spacing.py`에서 소수점/양수/100% 미만/0% 54가지×두 형식 **108쪽**과 160줄의 누적 쪽 나눔 **8쪽**이 96dpi·RGB 오차 0으로 전체 일치했습니다. 합성 일치의 역사적 누계는 **2,050쪽**이며 전체 누계를 한 번에 새로 시험했다는 의미는 아닙니다. 현재 관련 네 그룹(새 비율 간격 3개, 기존 이어지는 줄 1개, 소스 알파 5개, 인라인 간격 3개)은 12개 통과했습니다. 일반 검사는 130개 중 70개 통과·60개 건너뜀이며 보통 글꼴 202쪽·정밀도 4쪽과 설치 스킬의 24쪽 형식 쌍/29쪽 읽기·구조 검사도 유지됐습니다.

실제 7개·124쪽의 원본과 기준 SHA256, 쪽수·용지를 유지했습니다. `trip-hwpx`는 **4→0픽셀**, 첫 쪽과 둘째 쪽의 RGB 바이트 SHA256도 각각 기준과 같습니다. 그 결과 **전체 문서 1/7개, 쪽별 6/124쪽이 일치**합니다. 나머지 문서의 차이는 직전 커밋과 같고 회귀가 없었습니다. 전체 화면 무차이 목표는 여전히 미달성입니다.

## 고정·여백·최소 줄 간격의 단위 해석

HWP의 비율 외 줄 간격에서 단위 비트를 값으로 읽던 오류를 수정했습니다. 3.01pt의 명시적인 HWPUNIT 값은 301을 두 배 한 602로 기록합니다. HWPX의 직접/호환 case와 포장 값을 갖는 versioned default도 구분합니다. 구형·신형 문단 모양과 스타일 참조의 필드 구조는 [한컴 공식 파일 형식 문서](https://cdn.hancom.com/link/docs/%ED%95%9C%EA%B8%80%EB%AC%B8%EC%84%9C%ED%8C%8C%EC%9D%BC%ED%98%95%EC%8B%9D_5.0_revision1.3.pdf)를 확인했고 단위 비트·기준·반올림은 설치 한컴의 바이트·배치·PDF에서 추론했습니다.

글자 단위는 문서 기본 스타일 ID 0의 글자 참조에서 기준 크기를 읽습니다. 현재 글자나 현재 문단 스타일의 크기를 사용한다는 가설은 혼합 스타일 시험에서 기각했습니다. 기본 스타일의 글자 ID와 글자 모양 ID 0의 크기를 따로 바꾼 대조로 참조를 확인했습니다. 상대 크기 75%도 그 기준 크기는 바꾸지 않았습니다. 11pt에서 151 단위는 830.5를 831 HWPUNIT로 반올림하며, 반 단위를 계속 누적하던 첫 구현의 402픽셀 차이도 수정했습니다.

모델에서는 비율 외 간격을 pt로 정규화합니다. 새 파일·줄 간격 변경은 명시적인 HWPUNIT로 기록하고 HWPX의 직접/case/default 속성에도 같은 pt 의미를 적용합니다. 원본 보존에서 줄 간격을 바꾸지 않으면 기존 속성 바이트를 유지합니다. 전체 재작성은 현재의 pt 배치를 보존하며 원래 글자 단위의 상대 동작까지 재구성하지는 않습니다. 고정 간격이 글자 높이보다 작거나 0인 경우도 겹침을 유지합니다.

새 `test_line_spacing_units.py`에서 고정/여백/최소 24조건×두 형식 **48쪽**, 문서 기본 크기 11/20pt·선택 문단 스타일 3종·실제 글자 8/14pt·간격 종류 3종·글자 단위 3종의 **216쪽**이 전체 일치했습니다. 합성 누계에는 이 **264쪽만 추가**합니다. 버전 분기 HWPX 108쪽, 원본 보존 수정 234쪽과 구형 46바이트 문단 모양 8쪽은 중복 조건으로 별도 기록합니다. 이들을 포함한 새 시험의 전체 쪽 비교는 총 **614쪽**이며 614개의 고유한 신규 표본을 뜻하지 않습니다. 같은 pt 조건의 HWP/HWPX 쌍 24쪽도 독립 출력끼리 완전히 같습니다.

기존에 보존한 225쪽은 모두 일치했고, 앞서 미달성이었던 비율 외 36쪽도 여기에 포함됩니다. 기본 스타일이 글자 ID 0이 아닌 글자를 참조하는 별도 HWP 2쪽도 전체 일치했습니다. 최초 반 단위 잔여와 혼합 스타일 실패 로그는 보존하며 원래 기준 PDF는 교체하지 않았습니다.

새 단위 시험 7개는 최종 모듈·강화한 부분 검사·일반 검사의 합집합으로 통과했습니다. 한 번의 새 7개 실행으로 보고하지 않습니다. 기존 비율 3개·인라인 3개를 더한 관련 최종 검사는 13개이며 일반 137개 중 72개 통과·65개 건너뜀입니다. 보통 글꼴 202쪽·정밀도 4쪽, 설치 스킬의 24쪽 형식 쌍/29쪽 읽기와 구조 검사도 유지됐습니다. 합성 일치의 역사적 누계는 **2,314쪽**이며 새 전체 누계 시험 통과가 아닙니다.

실제 7개·124쪽의 원본/기준 SHA256, 쪽수·용지와 변경 픽셀 수는 직전 커밋과 같습니다. **전체 1/7문서·6/124쪽 일치**가 유지됐고 회귀는 없습니다. 실제 파일에는 글꼴 스타일·양쪽 맞춤, PNG 원본 알파 등의 차이가 남습니다. 앞선 새 한컴 5pt 장평 67픽셀과 좁은 폭/단어 줄바꿈 24쪽의 차이도 해결됐다고 주장하지 않습니다. 모든 한컴 작업은 순차 실행하고 묶음 뒤 Hwp.exe 0개를 확인했으며 메모리는 약 60~64%였습니다.


## 이어지는 양쪽 맞춤과 비트맵 끝 버퍼의 추가 검증
